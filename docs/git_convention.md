# Git 컨벤션

> 최종 프로젝트 팀 Git 사용 규칙
> 저장소 구조: **모노레포 + Gradle 멀티모듈**

---

## 1. 저장소 구조

```
project-root/
├── gateway-service/
├── user-service/
├── trading-service/
├── learning-service/
├── docker-compose.yml
├── prometheus.yml
└── README.md
```

### 모듈 간 의존 규칙

```gradle
// ❌ 절대 금지 — 서비스 모듈 간 직접 의존
implementation project(':trading-service')

// ✅ 공통 모듈만 허용
implementation project(':common')
```

> 물리적으로는 같은 저장소지만 서비스는 독립 배포된다.
> 다른 서비스의 패키지를 import하는 순간 분산 모놀리식이 된다.

## 2. 이슈와 브랜치

### 작업은 이슈에서 시작한다

**모든 작업은 이슈를 먼저 등록한 뒤 브랜치를 생성한다.**

| 이유 | 설명 |
|---|---|
| 진행 상황 공유 | 누가 무엇을 하는지 팀 전체가 확인 가능 |
| 중복 작업 방지 | 같은 기능을 두 명이 만드는 상황 차단 |
| 개발 기록보드 연동 | 이슈 목록이 곧 작업 이력 |
| PR 맥락 제공 | 크로스 리뷰 시 리뷰어가 배경을 파악 |

### 이슈 작성

**제목** — 커밋 메시지와 동일한 형식

```
[Learning] Kafka Consumer 멱등성 처리
[Trading] 시장가 매수 주문 체결
[공통] 응답 포맷 및 예외 클래스 정의
```

**본문**

```markdown
## 작업 내용
- 

## 완료 조건
- [ ] 
- [ ] 

## 참고
- 관련 문서, 이벤트 스키마 링크 등
```

> **완료 조건을 반드시 적는다.** "언제 끝난 것으로 볼지"가 없으면
> 이슈가 무기한 열려 있게 된다.

**라벨**

| 라벨 | 용도 |
|---|---|
| `feature` / `fix` / `chore` / `docs` | 작업 종류 |
| `user` / `trading` / `learning` / `gateway` / `infra` | 담당 영역 |
| `MVP` / `P1` | 우선순위 |

**담당자(Assignee)를 반드시 지정한다.**

---

### 브랜치 전략

| 브랜치 | 용도 | 삭제 |
|---|---|---|
| `main` | 배포 가능한 안정 버전 | 유지 |
| `develop` | 개발 통합 브랜치 | 유지 |
| `feature/*` | 기능 개발 | 머지 후 삭제 |
| `fix/*` | 버그 수정 | 머지 후 삭제 |
| `hotfix/*` | 배포 후 긴급 수정 | 머지 후 삭제 |

```
main ──────────────────────────●───────  (배포 시점)
                              /
develop ──●────●────●────●───●─────────
          \    \    \    \
     feature/  feature/  fix/  ...
```

- 기능 개발은 `develop`에서 분기해 `develop`으로 머지
- `main`은 시연·배포 시점에만 `develop`에서 머지

---

### 브랜치 네이밍

```
<타입>/<이슈번호>-<작업내용>
```

| 예시 | 설명 |
|---|---|
| `feature/12-kafka-consumer` | 12번 이슈, Consumer 구현 |
| `feature/15-market-order` | 15번 이슈, 시장가 주문 |
| `fix/23-idempotency-bug` | 23번 이슈, 멱등성 버그 수정 |
| `chore/7-github-templates` | 7번 이슈, 저장소 템플릿 |

**규칙**
- **이슈 번호를 반드시 포함한다**
- 소문자 + 하이픈(`kebab-case`)
- 한글 사용 금지
- 작업 내용은 3~4단어 이내로 축약
- 서비스명은 이슈 라벨로 구분하므로 브랜치명에서 생략

> 이슈 번호가 있으면 브랜치만 보고도 어떤 작업인지 추적할 수 있다.

---

### 작업 흐름

```
1. 이슈 등록 (담당자·라벨 지정)
        ↓
2. develop 최신화 후 브랜치 생성
        ↓
3. 작업 · 커밋
        ↓
4. PR 생성 (본문에 이슈 연결)
        ↓
5. 크로스 리뷰 → 승인
        ↓
6. develop 머지 → 이슈 자동 종료 → 브랜치 삭제
```

```bash
# 이슈 등록 후
git switch develop
git pull origin develop
git switch -c feature/12-kafka-consumer
```

---

### PR과 이슈 연결

PR 본문에 아래 키워드를 적으면 **머지 시 이슈가 자동으로 닫힌다.**

```markdown
Closes #12
```

| 키워드 | 동작 |
|---|---|
| `Closes #12` / `Fixes #12` | 머지 시 이슈 자동 종료 |
| `Related to #12` | 연결만 하고 종료하지 않음 |

> 이슈 하나에 PR 여러 개가 필요하면 마지막 PR에만 `Closes`를 쓴다.

## 3. 커밋 메시지

### 형식

```
<타입>: <제목>

<본문 (선택)>
```

### 타입

| 타입 | 용도 |
|---|---|
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 기능 변경 없는 코드 개선 |
| `test` | 테스트 코드 추가·수정 |
| `docs` | 문서 수정 |
| `chore` | 빌드, 설정, 의존성 |
| `style` | 포맷팅, 세미콜론 등 (동작 변경 없음) |
| `perf` | 성능 개선 |

### 제목 규칙

- 50자 이내
- 한글로 작성
- 마침표 없음
- 명령형 대신 **완료형**으로 통일 (`추가`, `수정`, `제거`)

### 예시

```
feat: Kafka Consumer 멱등성 처리 추가

event_id UNIQUE 제약으로 중복 소비를 차단한다.
애플리케이션 레벨 SELECT 후 INSERT는 동시 처리 시
뚫릴 수 있어 DB 제약으로 처리했다.
```

```
fix: 손절 준수 판정 시 계획 손절가 NULL 처리

손절가 미입력 포지션이 위반으로 잘못 판정되던 문제 수정
```

```
refactor: 진단 규칙을 DiagnosisRule 인터페이스로 분리
```

```
chore: docker-compose에 Kafka-UI 추가
```

### 본문 작성 기준

**"무엇"보다 "왜"를 적는다.** 무엇을 바꿨는지는 diff를 보면 안다.

- 왜 이 방식을 선택했는지
- 고려했다가 버린 대안이 있는지
- 주의할 부작용이 있는지

> 여기 적은 내용이 나중에 개발 기록보드와 브로셔의 재료가 된다.

## 4. Pull Request

### PR 크기

| 크기 | 리뷰 품질 |
|---|---|
| ~100줄 | 꼼꼼히 본다 |
| ~300줄 | 볼 만하다 |
| 500줄+ | 형식적 승인이 된다 |

**300줄 이내를 권장한다.** "기능 하나 = PR 하나"로 쪼갠다.

### PR 제목

커밋 메시지와 동일한 형식을 사용한다.

```
feat: Learning 서비스 매수 이벤트 소비 구현
```

## 5. 코드 리뷰

### 승인 규칙

**모든 PR은 최소 1명의 승인을 받아야 머지할 수 있다. 셀프 머지는 금지한다.**

### 리뷰어 지정 — 서비스 간 크로스 리뷰

리뷰어는 **다른 서비스를 담당하는 팀원**으로 지정한다.

| 작성자 서비스 | 리뷰어 |
|---|---|
| User | Trading 또는 Learning 담당 |
| Trading | User 또는 Learning 담당 |
| Learning | User 또는 Trading 담당 |

**이유**
- 프로젝트에서 사용된 기술을 팀원 전체가 설명할 수 있어야 한다
- 자기 서비스만 알면 기술 면접에서 답할 수 없다
- 서비스 경계 침범(다른 서비스 패키지 import)은 외부인이 더 잘 발견한다

### 경계에 걸친 PR

아래 항목은 **해당 서비스 담당자를 반드시 리뷰어에 포함**한다.

| 대상 | 필수 리뷰어 |
|---|---|
| 이벤트 스키마 변경 | Trading + Learning 양쪽 |
| 공통 모듈 (응답 포맷, 예외, BaseEntity) | 인프라 담당 |
| Gateway 라우팅 | 인프라 담당 |
| DB 스키마 변경 | 해당 서비스 담당 |

### 리뷰 데드라인

**PR 등록 후 24시간 이내에 리뷰한다.**

리뷰가 지연되면 작성자가 직접 리뷰어에게 요청한다.
리뷰 대기로 작업이 막힌 경우 스크럼에서 공유한다.

> 최소 1명 승인이 강제이므로, 리뷰를 미루면 팀 전체 속도가 느려진다.
> PR을 작게 쪼개는 것이 리뷰 속도를 높이는 가장 확실한 방법이다.

### 크로스 리뷰를 위한 PR 작성 요령

다른 서비스 담당자는 도메인 맥락이 없다. **PR 본문에 맥락을 적는다.**

- 이 작업이 어떤 흐름의 일부인지 한 줄
- 왜 이 방식을 선택했는지
- 리뷰어가 특히 봐줬으면 하는 부분

```markdown
## 작업 내용
Kafka Consumer에서 매수 체결 이벤트를 받아 스냅샷으로 저장한다.

## 변경 이유
Learning은 Trading DB를 직접 조회하지 않으므로,
이벤트로 받은 데이터를 자체 테이블에 보관해야 한다.

## 리뷰 포인트
- event_id UNIQUE로 중복 소비를 막는 방식이 적절한지
- 예외 발생 시 오프셋 커밋 처리
```

### 코멘트 등급

| 표기 | 의미 |
|---|---|
| `[P1]` | 머지 전 반드시 수정 |
| `[P2]` | 고치면 좋음, 판단은 작성자 |
| `[P3]` | 취향 의견, 무시해도 됨 |

```
[P1] 동시 요청 시 잔고가 음수가 될 수 있습니다
[P2] 이 메서드 이름이 하는 일과 다른 것 같아요
[P3] 여기 개행 하나 있으면 읽기 편할 듯합니다
```

> P3에 부담을 느끼지 않는 것이 이 표기의 목적이다.

### 즉시 반려 대상

| 항목 | 이유 |
|---|---|
| 다른 서비스 패키지 import | 서비스 경계 침범 |
| 금액에 `double` / `float` 사용 | 부동소수점 오차 |
| 시각에 `LocalDateTime` 사용 | 타임존 정보 소실 |
| `@Transactional` 내부에서 외부 호출 | 트랜잭션 장기 점유 |
| 시크릿·API 키 하드코딩 | 보안 |

## 6. 머지 전략

| 대상 | 방식 |
|---|---|
| `feature` → `develop` | **Squash and merge** |
| `develop` → `main` | **Merge commit** |

- Squash로 커밋 히스토리를 기능 단위로 정리한다
- 머지 후 feature 브랜치는 삭제한다
- **강제 푸시(`--force`)는 공유 브랜치에서 금지**

### 충돌 해결

```bash
git switch feature/learning-xxx
git fetch origin
git rebase origin/develop
# 충돌 해결 후
git push --force-with-lease
```

> 개인 feature 브랜치에서만 rebase를 사용한다.
> `--force-with-lease`를 사용해 남의 커밋을 덮어쓰지 않는다.

## 7. 팀 합의 사항

| 항목 | 결정 |
|---|---|
| 저장소 | 모노레포 + Gradle 멀티모듈 |
| 기본 브랜치 | `develop` |
| **작업 시작** | **이슈 등록 후 브랜치 생성** |
| **브랜치 네이밍** | **`<타입>/<이슈번호>-<작업내용>`** |
| 머지 방식 | Squash and merge (feature → develop) |
| PR 최소 승인 | **1명 (셀프 머지 금지)** |
| 리뷰어 지정 | **다른 서비스 담당자 (크로스 리뷰)** |
| 리뷰 데드라인 | 24시간 |
| 커밋 메시지 언어 | 한글 |
